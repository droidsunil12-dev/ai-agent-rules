## Current
- Repo: `C:\Users\Doraemon\Desktop\Jarvis\repo`. A Node "bridge" app that (a) serves a built static UI and (b) routes LLM traffic through a pluggable "brain" engine. Three engines: `claude` (default, MCP tools), `gemini` (Google AI Studio), and `openai` (any `/v1/chat/completions` provider — OpenAI, Groq, OpenRouter, Ollama, LM Studio, etc.). Single-container "Dograh" mode serves the built UI on one port.
- `.cmd` shims broken in this environment: `npm run build` and `npx tsc` fail with "The system cannot find the path specified" because the `.cmd` shims in `node_modules\.bin\` (tsc.cmd, vite.cmd) don't resolve under this PC's bash/PowerShell environment. Working pattern: call the JS entrypoints directly with node — `node node_modules/typescript/bin/tsc -b` (type-check) and `node node_modules/vite/bin/vite.js build` (Vite bundle). Affects any project on this PC whose `npm run <script>` wraps a `.cmd`-based binary.
- Static UI serving: in the single-container Dograh mode, `GET /` must explicitly map to `index.html`, not the dist directory. The original handler resolved the relative path `''` against `UI_DIST` and produced the dist *directory itself* → `readFile` threw `EISDIR: illegal operation on a directory`, so every page load returned 500 "ui read failed". Fix: `urlPath === '/' ? 'index.html' : urlPath` before computing the safe path. Re-check if the static-serving block is refactored.
- Config precedence: env var > config file > baked-in default, via a `resolvePath_(envVal, fileVal, fallback)` helper (the original `cfgAt(path, fallback)` wrongly let the config file win over env vars, breaking `JARVIS_BRAIN_ENGINE` and Docker-compose env overrides).
- Engine/model family guard: a model name from one engine family must NOT be sent to a different engine's API. E.g. a Claude model name (`claude-opus-5`) pinned in the config file must NOT be sent to the Gemini or OpenAI API. The `EFFECTIVE_BRAIN_MODEL` guard checks the model's family prefix against the active engine and falls back to the engine's default (`gemini-2.5-flash` for Gemini, `gpt-4o-mini` for OpenAI) on mismatch. Without the guard, switching the brain engine via env while the file still holds a foreign model silently sends the wrong model name to the wrong API.
- OpenAI-compatible brain (`bridge/openai.mjs`): `openaiBrain(socket, { base, model, key })` hits `base + "/chat/completions"` with `stream: true`, parses SSE `data:` lines for `choices[0].delta.content`, sends `{type:'text', text}` frames per chunk, `{type:'done'}` on completion, `{type:'error'}` on failure. No MCP tools (Claude only). Config: `brain.openaiBaseUrl` (default `https://api.openai.com/v1`), `brain.openaiApiKey` (env `OPENAI_API_KEY` / `JARVIS_OPENAI_API_KEY`), default model `gpt-4o-mini`. Settings UI (gear icon) shows three brain engine options; selecting `openai` reveals base URL + API key fields.
- Voice pipeline: VAD trigger threshold `TRIGGER_OVER_FLOOR` in `src/lib/vad.ts` was lowered from `2.6` → `2.2` (too strict for quiet laptop mics in quiet rooms; the voice-activity detector's threshold = floor × multiplier was above the user's speaking energy so the trigger never fired). STT routing: `STT_ENGINE = "auto"` resolves to Google STT when a Google key is present, else falls through to ElevenLabs Scribe (returns 503 if no key). `STT_ENGINE = "browser"` in `jarvis.config.json` forces the browser's built-in `SpeechRecognition` API (no server-side transcription), but the `capabilities.ts` probe must report `stt: false` (which only happens when no Google key AND no ElevenLabs key are configured); with a Google key present, `auto` resolves to Google STT automatically. `Capabilities.stt` boolean in `voice.ts` is the switch: `caps().stt ? startElevenVoice(h) : startBrowserVoice(h)` — when the bridge's `/health` returns `stt: true`, it always uses the VAD + server-side transcription path, not `SpeechRecognition`. If the bridge is not running or no STT key is configured, `/stt` returns 503 and `transcribe()` in `voice.ts` silently drops the segment with `diag.lastError = "stt 503"` — the user sees no feedback, just silence. Fix: ensure the bridge is running AND either configure a Google key (Settings → Keys → Google key) or accept the browser `SpeechRecognition` fallback (less reliable). A "play sample" TTS preview button in Settings calls `POST /tts` with `{text}` and plays the returned audio blob inline so the user can verify voice before committing to a choice.
