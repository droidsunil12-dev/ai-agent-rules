- **GitHub Actions free-tier economics (durable, cross-project):** on private repos, Free tier provides 2,000 billing minutes/month; Windows-hosted runners consume a **2× multiplier** (1 wall-clock min = 2 billed min). A single 6-hour Cloud PC session consumes 720 billed minutes (~35% of monthly quota) — the entire monthly allowance is exhausted in ~16.6 total hours of runtime. When quota hits 100%, newly dispatched workflows fail immediately at queue time (no runner provisioned; run shows failed with empty jobs/steps + 404 log blobs). GitHub Actions also enforces a strict **hard ceiling of 360 minutes (6 hours) per job** — the runner is abruptly terminated and the VM destroyed regardless of any keep-alive loop.
- **Windows profile directory collision:** pre-creating directories under `C:\Users\<username>` (Desktop, `.ssh`, etc.) before the user's first login causes Windows User Profile Service to detect an invalid existing directory without `NTUSER.DAT`. The user's RDP session then provisions a *collided* profile: `C:\Users\<username>.<COMPUTERNAME>` (e.g. `C:\Users\RDPUser.runnervmm7ud1`). Scripts expecting files in `C:\Users\<username>\AppData\Local` fail to see them. Use dynamic `$env:LOCALAPPDATA` / session-relative paths, not hardcoded `C:\Users\<name>\...`.
- **Windows Sandbox micro-VM (for isolated AI agent execution):** requires `Containers-DisposableClientVM` optional feature enabled via elevated DISM (`dism /online /Enable-Feature /FeatureName:Containers-DisposableClientVM /All /NoRestart`) + reboot before `.wsb` files execute. Sandbox resets all disk changes on exit; persist data by mounting a writable host folder via `.wsb` `<MappedFolder>` + `<LogonCommand>` directory junctions (`mklink /J "%LOCALAPPDATA%\<app>" "C:\SandboxWorkspace\<app>"`). Sandbox lacks the WebView2 runtime — applications using embedded web components (e.g. Hermes Setup UI) fail with "Could not find the WebView2 Runtime"; download `MicrosoftEdgeWebview2Setup.exe` into the mapped workspace and run it `/silent /install` in the logon script. Stale `gateway_state.json` carried over from prior VM shutdowns must be purged, otherwise the desktop app treats a dead PID as an active gateway and stalls. User prefers WSL2 + WSLg borderless single-window UI over Windows Sandbox's full nested desktop, provided hardware hypervisor isolation remains intact.
- **WSL2 DrvFs rejects virtual cloud drive letters:** `mount -t drvfs <letter>: <path>` only supports physical NTFS/FAT partitions. Virtual filesystem drivers (TeraBox Drive via WinFsp/Dokan on `T:\`) fail DrvFs mounting with `bad option; for several filesystems you might need a /sbin/mount.<type> helper program`. Share files between WSL2 and cloud storage by placing them on a physical Windows partition (`/mnt/c/Users/<user>/...`) rather than direct guest DrvFs mounts of virtual drive letters.
- **Runner direct-download helper:** transferring multi-MB installer binaries over Tailscale SMB to an ephemeral cloud runner frequently times out over residential uplinks. Writing a lightweight `.bat` script onto the runner's desktop via SMB that invokes PowerShell `Invoke-WebRequest` to download directly from GitHub Releases (and run silent install flags) bypasses the client upload bottleneck by using the runner's datacenter bandwidth.
- **Windows standard user has no write access to `C:\`:** batch scripts running as a standard interactive user that try to write to `C:\` fail with `Access is denied`. Use `C:\Users\Public` or `%TEMP%` instead. Long-running compression tools (7-Zip) in interactive batch scripts should use real-time progress flags (`-bsp1`, `-mx=1`) rather than full stdout redirection, to prevent users from mistaking a blank window for a hang.

- **RDP clipboard fix on the cloud PC:** when clipboard copy-paste fails in BOTH directions (PC↔laptop), the RDP connection file (`CloudPC.rdp`) is usually NOT the cause — `display connector clipboarding:i:1` is already set. The #1 cause is the remote **`rdpclip.exe`** (RDP Clipboard Monitor) process wedging/dead on the runner. Fix inside the session: Task Manager → Details → end `rdpclip.exe`, then File → Run new task → `rdpclip.exe`; if still dead, logoff + reconnect (re-negotiates the channel). `rdpclip.exe` re-launches on each RDP connect, so an existing wedged session needs a restart. Quick file-transfer workaround when clipboard stays dead: write content to a file on the PC and read it back, bypassing the clipboard channel entirely. Web-based RDP viewers do NOT support clipboard redirect; use built-in `mstsc.exe` (Win→R) for clipboard to work at all. `redirectclipsbrd:i:1` is **not a valid RDP connection-file key** — RDP silently ignores it; the clipboard channel is controlled by `mstsc.exe`'s Local Resources → Clipboard checkbox + the remote `rdpclip.exe` process. - **GitHub Actions token gotcha (durable):** `GITHUB_TOKEN` auto-injected into a job is **read-only** on public repos — `PUT .../contents/...` with it returns **401 Bad credentials**. Use a user PAT (here `HERMES_PUSH_TOKEN` secret) for any write to a repo from inside a workflow. The token must be wired into the job's `env:` block or the step sees `$null`. Hardcoded PATs in committed YAML get blocked by GitHub **Push Protection** (secret-scanning rule GH013) — the push is rejected until the secret is removed from the commit or unblocked at the repo's secret-scanning URL. - **Concurrent keep-alive tick race:** the 10-min routine ticks can overlap (each Case B down path takes 6+ min), so multiple ticks race on shared `state.json`, the routine memory file, and dispatching. Rule: always re-read `state.json` + `GET /actions/runs?per_page=5` fresh at tick start and act on that, not on the shared routine memory; when editing the shared memory, read it again immediately before writing and only touch the specific lines you intend. A cancel POST on an already-ended run returns **409 (Conflict)** — expected/harmless, not an error. A `POST .../dispatches` that just fired can return a `GET .../actions/runs?per_page=1` that is NOT your dispatch (a pre-existing or another tick's run); list `?per_page=5` with `created_at`/`status` and follow the only one still `in_progress`.
