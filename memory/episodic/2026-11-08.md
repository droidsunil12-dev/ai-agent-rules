## 00:50 Hermes installer is a Rust bootstrapper; silent flags fail and require direct binary placement
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
`Hermes-Setup.exe` is a Rust-based installer (`hermes_bootstrap_lib`), not Inno Setup or NSIS. It ignores silent flags like `/VERYSILENT`, `/SILENT`, and `/S`, stalling or terminating without extracting files when executed on a headless GitHub Actions Windows runner. Durable solution on ephemeral runners: copy the bundled installer binary directly to `C:\Users\RDPUser\Desktop\Hermes.exe` and `Hermes-Setup.exe`, target desktop and Start Menu shortcuts there, and verify file presence explicitly before publishing connection details.

## 00:50 Windows runner OpenSSH requires Administrators membership for remote verification

## 01:25 Pre-creating user profile folders causes Windows profile directory collision
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
Pre-creating directories under `C:\Users\<username>` (such as `Desktop` or `.ssh`) before the user logs in for the first time causes Windows User Profile Service to detect an invalid existing directory without `NTUSER.DAT`. When the user subsequently connects via RDP, Windows provisions a separate collided profile directory: `C:\Users\<username>.<COMPUTERNAME>` (e.g. `C:\Users\RDPUser.runnervmm7ud1`). Scripts or automations expecting files in `C:\Users\<username>\AppData\Local` fail to see files created during the interactive session. Dynamic checks or scripts running inside the user session (`$env:LOCALAPPDATA`) must be used to locate the active profile.

## 01:40 Windows standard user lacks write permissions to root C:\; use C:\Users\Public for scripts
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
On Windows Server, standard interactive users lack write permissions to create new files in the root directory (`C:\`). Batch scripts executed by standard users that attempt to write output files or archives directly to `C:\` fail with unhandled `Access is denied` errors. User-facing utility scripts must write to universally writeable paths such as `C:\Users\Public` or `%TEMP%`. Additionally, interactive batch scripts invoking long-running compression tools like 7-Zip should avoid full stdout redirection and instead use real-time progress flags (`-bsp1`, `-mx=1`) to prevent users from mistaking a blank command window for a hang and cancelling the process.

## 09:10 Windows Sandbox micro-VM for isolated AI agent execution requires DISM feature enablement
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
To execute autonomous AI agents (such as Hermes) with terminal capabilities safely on a local Windows 11 Pro host without risking host file access or consuming GitHub Actions runner quotas, Windows Sandbox (`.wsb`) provides disposable hardware-isolated virtualization with host folder mapping. ## 09:45 Windows Sandbox state persistence via directory junctions to mapped host storage
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
Windows Sandbox micro-VMs reset all disk changes on exit, but applications can persist data across restarts by mounting a writable host folder via `.wsb` `<MappedFolder>` and having `<LogonCommand>` create directory junctions (`mklink /J "%LOCALAPPDATA%\<app>" "C:\SandboxWorkspace\<app>"` and `mklink /J "%USERPROFILE%\.<app>" "C:\SandboxWorkspace\<app>"`). For Hermes Agent specifically, the unpacked desktop app binary resides at `<base>\hermes-agent\apps\desktop\release\win-unpacked\Hermes.exe` and expects `%LOCALAPPDATA%\hermes` to resolve to the agent backend and config files. Additionally, any stale `gateway_state.json` carried over from prior VM shutdowns must be purged, otherwise the desktop app treats the dead process PID as an active gateway and stalls connection.

## 15:35 Inbox wsl.exe stub rejects distribution flags on uninstalled systems
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
On Windows systems where WSL is not yet installed, `wsl.exe` is an inbox stub binary supporting only `--install`, `--update`, `--status`, and `--help`. ## 16:25 WSL2 DrvFs rejects virtual cloud drive letters like TeraBox T:\
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
WSL2 DrvFs (`mount -t drvfs <letter>: <path>`) only supports physical local drives (such as NTFS/FAT partitions). Virtual filesystem drivers and cloud mounts mapped to Windows drive letters (such as TeraBox Drive via WinFsp/Dokan on `T:\`) fail DrvFs mounting with `bad option; for several filesystems (e.g. nfs, cifs) you might need a /sbin/mount.<type> helper program`. Sharing files between WSL2 and virtual cloud storage requires placing files on a physical Windows partition (such as `/mnt/c/Users/<user>/...`) rather than attempting direct guest DrvFs mounts of virtual drive letters.

## 16:45 NousResearch hermes-agent setup requires repository checkout and produces local root launcher
Reference: sessions.get("Zc1lMNKF7V3eCgTl")
The upstream `NousResearch/hermes-agent` setup script (`setup-hermes.sh`) cannot be piped directly into `bash` from a standalone URL because it depends on `pm/lock.json` and repository configuration files in the working directory.
